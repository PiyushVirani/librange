LibRange plan:


Description

A web application* that reduces the time (by x%**) it takes to find books and items in the MacOdrum Library.

*: a final version of this would most probably be a web-app, initial prototypes may NOT be web based

**: the exact percentage improvement would be calculated and updated

Requirements


Functional requirements
1. The system must allow users to paste the call number into a textbox to view the range number
2. The user must be able to view the location of a particular book on a map of MacOdrum library based on the range number

Non-functional requirements
1. No authentication required
2. Must be available on web via a user interface
3. Must be developed using React.js
4. Should be well documented (readme, comments, etc.)

The guide to call numbers for this project:

Library of Congress Tutorial - Call Number and Shelving

* The first line is always a Letter Line and is filed alphabetically.
* A call number may not start with 4 or more consecutive letters.
* The second line is a Whole Number line and is filed numerically.
* This number may have a maximum of 4 digits before the first decimal point. If there is no decimal point, it may still have a maximum of 4 digits.
* Sometimes the second line is decimalized and continued on the same line or on the third line. Anytime you see a decimal point, always take each space separately (do not consider it a whole number).
* However, generally the third line is a Cutter Line. It begins with a decimal, then a letter. Always read each digit separately in the Cutter Line. Remember if there is a decimal point, take one space at a time. The Cutter Line may also be split on two lines, but when this occurs there is only a decimal point at the very beginning of the Cutter Line.
* Other lines may include volume numbers, copy numbers, dates or a combination.
* Letters before numbers.
* Nothing comes before something.
* No date comes before a date.
* Volumes are compared before copies.
* Copies are compared before dates.
* x ("little x") represents 1/2 - it comes after the letters but before numbers.

Modules


What the app does (tight scope)
User pastes a call number -> system determines the range -> UI highlights that range on a MacOdrum map and shows a "go here" location.
________________


Suggested modules (fills your "Modules: To be done")
1) UI Module (React)
Goal: Take input, show result, render the map highlight.
* CallNumberForm
   * textbox + submit
   * basic validation ("empty", weird characters)
* ResultPanel
   * displays interpreted call number, computed range, floor/section, notes
* MapView
   * displays library map image/SVG
   * highlights the computed range area
* AppShell
   * layout + state management glue
State shape idea:
callNumberInput: string
parsedCallNumber: ParsedCallNumber | null
matchResult: RangeMatch | null
error: string | null


________________


2) Call Number Parsing Module
Goal: Convert a pasted call number into something comparable.
Create a utility like:
* parseCallNumber(raw: string) -> ParsedCallNumber
What it should do (minimum viable):
* normalize spacing/case
* split into parts (letters, number, cutter, year, etc.)
* produce a sortable "key" form (even if it's rough at first)
You can start simple (string normalization + lexical compare), then improve later if you find edge cases.
________________


3) Range Lookup Module
Goal: Given a parsed call number, find the range record.
* findRange(parsed: ParsedCallNumber, ranges: RangeRecord[]) -> RangeMatch | null
RangeRecord example:
id, startCall, endCall, floor, sectionName, mapRegionId, notes


Lookup approach:
* keep ranges sorted by start key
* do a binary search, or just linear scan if dataset is small (fine for a prototype)
________________


4) Map Highlighting Module
Goal: Highlight the shelf region on the map.
Two practical options:
1. SVG map (best)
   * each range is a <path id="RANGE_A1">...
   * highlight by applying a CSS class to the matching mapRegionId
2. PNG/JPG map with overlay boxes (fastest)
   * store rectangles/polygons for each range region
   * draw overlay with absolute-positioned divs or canvas
For your React requirement and simplicity, SVG is usually the cleanest.
________________


5) Data Module (Ranges dataset)
Goal: Store and load the call-number-to-range mapping.
Start with:
* ranges.json checked into the repo
Later upgrades:
* editable admin sheet -> exported JSON
* small backend, but your requirements don't need one
________________


6) Docs + Quality Module
Matches your "well documented" requirement.
* README: setup, run, how ranges are represented, how to add/edit ranges
* comments in parsing + lookup code (those are the tricky parts)
* short "Assumptions & Limitations" section (call numbers can be messy)
________________

Sequence of Events
1. The user enters the call number of a book into the form, and submits it
2. The system processes the call number and finds the corresponding range number
3. The system sends the range number to the UI
4. The UI updates the map with the desired range highlighted

Phases
Phase 1: Data Modeling & Core Logic
The "Brain": Establishing how call numbers are compared and stored.

Define TypeScript Interfaces

Tech: TypeScript (src/types/)

Action: Fill in RangeRecord.ts and ParsedCallNumber.ts. You need a standard way to represent a call number (Class letters, subclass numbers, cutter, etc.) and a range (Start key, end key, floor, map ID).

Implement the Normalization Engine

Tech: TypeScript / Regex (src/lib/callNumberKey.ts)

Action: Write a function that converts a human-readable call number (e.g., "QA 76.73") into a sortable string key.

Tip: Pad numbers with leading zeros (e.g., QA 76 becomes QA0076) so that QA 100 correctly sorts after QA 20.

Create the Parsing Logic

Tech: TypeScript (src/lib/parseCallNumber.ts)

Action: Write the logic to regex-split the user's input into the segments defined in your project plan (Letters, Numbers, Cutters).

Populate Sample Data

Tech: JSON (src/data/ranges.json)

Action: Add 5–10 real range entries from the MacOdrum Library. Each entry should have a startKey and endKey generated by your normalization engine.

Phase 2: State & Search
The "Connective Tissue": Finding the right range based on input.

Develop the Range Lookup Algorithm

Tech: TypeScript (src/lib/findRange.ts)

Action: Write a function that takes the user's "Key" and iterates through the ranges.json to see if the key falls alphabetically/numerically between a startKey and endKey.

Set up Central State Management

Tech: React Hooks (src/App.tsx)

Action: In App.tsx, use useState to hold the searchQuery, the matchResult, and any error messages. This state will be passed down to your components as props.

Phase 3: User Interface Development
The "Face": Making the app usable and visual.

Build the Input Form

Tech: React / HTML5 (src/components/CallNumberForm.tsx)

Action: Create a text input and a submit button. Implement basic validation to ensure the input isn't empty before triggering the search.

Build the Result Display

Tech: React / CSS (src/components/ResultPanel.tsx)

Action: Create a component to show the "Found it!" message, displaying the Floor, Range Number, and the "Parsed" version of the call number so the user knows the system understood them.

Create the Interactive Map

Tech: React / SVG (src/components/MapView.tsx)

Action: This is the most visual part. Use an SVG of the library floor plan. Give each shelf/range a unique id.

Logic: If matchResult.mapRegionId === 'range-A1', apply a CSS class to that SVG element to change its color to red or yellow.

Phase 4: Refinement & Deployment
The "Polish": Ensuring a smooth user experience.

Error Handling & Edge Cases

Tech: TypeScript

Action: Handle cases where a call number is valid but doesn't exist in your database, or where a user enters "UrbLib" (which your plan says to ignore).

Styling and Layout

Tech: CSS / Flexbox

Action: Ensure the UI works on mobile. Students often carry their phones while looking for books in the stacks, so a vertical "Form on top, Map on bottom" layout is essential.

Build and Host

Tech: Vite / GitHub Pages or Vercel

Action: Run npm run build and deploy the dist folder to a hosting provider so it can be accessed via a URL.
